How Winnow works

Winnow is a self-hosted lead generation platform for agencies. It finds contact addresses on the websites you point it at, keeps them in lists you control, sends your own email from your own mailboxes, and watches those mailboxes to see who replied.

Nothing is sent to a third-party service. There is no per-lead fee, and no third party holds your prospect list. Everything runs on a machine you control.

This page explains the whole thing in plain language: what each part does, how the data flows, and what happens when something goes wrong.

version 0.1.0 Java 21 / Spring Boot 3.5 MySQL 8 AGPL-3.0 self-hosted

Part oneWhat it is for

An agency running outbound campaigns has a repetitive problem. It needs to find people who might buy something, put them into a list, write emails to them, send a lot of those emails, and then notice who answered. Every step of that is mechanical, and every step of it is where the cost and the risk live.

Winnow does those four steps. That is the whole product.

Find people

You upload a spreadsheet of website addresses. The system visits each site, reads the raw HTML, and pulls out any email addresses it can find. Those become a list you can export as a spreadsheet.

Organise them

Those addresses, plus any you typed in yourself, become clients. You sort clients into named groups, so you can send to one group and deliberately not to another.

Send to them

You write an email once, as a rich text document, and a second person approves it. Then you pick a group, pick which mailbox it goes out from, and press send. The system works through them one at a time and records how each one went.

Catch the replies

A background job connects to each of your mailboxes, reads the new mail, and stores it, so you can see who answered and what they said.

Why self-hosted matters here. A prospect list is a business asset. If a third-party service holds it, so does everyone that third party works with. Running your own means the list lives on your hardware, the mail goes out from mailboxes you already own and pay for, and the per-lead fees other tools charge are simply not part of the running cost.

Part twoHow the whole thing fits together

Here is a day in the life of the system, as if you were watching it work.

1. You sign inYour username and password. Nothing else is asked for: no licence key, no activation code, no machine fingerprint. Your account carries a role, and the role decides what you can do.
↓
2. You build a client listUpload a spreadsheet of names and addresses, or add a group by hand. Each column is read from the column it belongs to, and a malformed row is reported back to you rather than silently skipped.
↓
3. You write a templateA rich text email with its own subject line. It starts as a draft. You submit it, a manager approves it, and only then can it be used. If somebody edits an approved template, it goes back for approval again.
↓
4. You register your mailboxesFor ordinary sending: an address, a mail server, a port and an app password. For Google: the account address and an OAuth client. The passwords themselves are never typed into the database - see the security section.
↓
5. You press sendThe system resolves the recipients inside your group, checks the sending limits, creates one delivery record per recipient, and hands the job to a background worker. That worker sends each message, records success or failure against that recipient, and updates the campaign totals as it goes.
↓
6. Separately, you look for leadsUpload a spreadsheet of domains. A bounded pool of workers visits each one, checks the address is safe to visit, reads the page, and extracts the addresses on it. Results are written in batches, and the same address is never stored twice in one run.
↓
7. Separately, the scheduled work runsEvery minute the outbox worker looks for messages whose time has come and sends them. Every few minutes the inbox worker polls your mailboxes for new mail. A third worker advances any lead extraction that is still running.

Part threeSeveral agencies, one installation

More than one company can use the same installation. Each signs in with its own account, and each sees only its own data. That is the single most important property of the whole system, so it is worth being precise about how it works.

The tenant is the signed-in user

Not a value in a session, not a value in a form, not a value the browser sends. It is read from the security context on the server, on every single request, and it is passed explicitly into every service call as the first argument. A request has no way to choose its own tenant.

The database filters on it again

Every query that returns tenant data filters on the owner, and every query that changes tenant data requires the owner. A record belongs to exactly one tenant, and the foreign keys are real ones, so a row cannot end up attached to the wrong owner.

It is tested, not assumed

There is a test file with 75 checks that proves one tenant cannot read or change another tenant's data, covering every repository method and every mutating operation in the system. If somebody adds a new endpoint and forgets the filter, the build fails.

The roles

RoleCan do
ROLE_VIEWERRead everything in their own account, and change nothing.
ROLE_OPERATOREverything a viewer can do, plus editing clients, groups, templates and sending accounts, and running campaigns.
ROLE_MANAGEREverything an operator can do, plus approving or rejecting templates.
ROLE_ADMINEverything, including managing users and sending accounts.

Part fourFinding leads

This is the part that needs the most care, because it is the part that goes and visits websites you did not build.

What happens when you upload a list of domains

  1. The list is read

    Column A of the spreadsheet is the domain. Blank rows are skipped, and the run records how many domains it accepted.

  2. Each address is checked before it is visited

    Only http and https are allowed. The host name is resolved and every address it resolves to is checked. Anything pointing at a private network, the loopback interface, or the cloud metadata address is refused, and that refusal cannot be switched off. If an operator has set a list of permitted domains, anything outside it is refused too.

  3. The page is fetched with a time limit

    Five seconds to connect, ten to read, and a cap on how large a response may be. A redirect is followed at most twice, and each hop is checked again. A site that hangs or points somewhere unexpected cannot hold a worker open or take the system somewhere it should not go.

  4. Addresses are pulled out and kept only if they belong

    The page is scanned with a conservative pattern. An address is kept only if its domain matches the domain that was crawled, so a page that links to a partner does not drag that partner into your list.

  5. Results are written in batches

    Hundreds at a time, never one insert per address. The same address is stored once per run, enforced by the database rather than by memory, so a run that is repeated behaves the same way every time.

  6. The run always ends

    Success, partial, or failed. A domain that cannot be reached is counted and does not fail the run. The status is never left hanging.

What is deliberately not here. Winnow reads public pages. It does not log in anywhere, does not work around a block, and does not fetch a site that asks it not to. There is a second, separate tool in the project for reading Amazon search results through a real browser; it runs as its own service on your own machine, reached only over loopback.

Part fiveSending

There are two ways to send, and they suit different situations.

Route one

A campaign

You pick a group, a template and a sending mailbox. The system resolves the recipients, creates a delivery record for each, and a background worker sends them one at a time. You can watch the progress, and you can cancel it. Each recipient gets their own record saying sent or failed, with the reason if it failed.

Route two

The outbox

You schedule individual messages for a time in the future. A background worker picks them up when they are due. Each row is claimed with a conditional update, so a message is never sent twice even if two application instances are running at the same time.

The rules the sender works to

  • Separate limits, measured properly. A daily limit, an hourly limit and a monthly limit, per account and per sending mailbox, counted from the system's own delivery records in real calendar windows. A limit labelled daily and counted monthly is a limit nobody can reason about.
  • Timeouts on every connection. Fifteen seconds to connect, thirty to read, thirty to write. Without them, one quiet mail server holds a worker open indefinitely.
  • One message per recipient. Each message is built fresh, so a failure halfway through cannot leave anything behind for the next recipient.
  • One bad recipient does not stop the batch. The failure and its reason are recorded against that recipient, and the campaign carries on.
  • The subject is its own field. It is validated, and it is never derived from something else.
  • Plain text as well as HTML. Every message carries both, so it survives mail clients that will not show HTML.
  • Your variables are escaped. A value substituted into the body is HTML-escaped, so a value that contains markup shows up as text rather than as markup.

Part sixCatching the replies

The inbox worker connects to each registered mailbox, reads what has arrived, and stores it. The details that matter:

  • It only reads new mail. It picks up from where the last poll finished, rather than asking for everything ever sent.
  • It never stores the same message twice. Each message has an identifier from the mail provider, and the database refuses a duplicate. Polling twice changes nothing.
  • It does not block. The connection has a timeout, and the folder is always closed afterwards, even when something went wrong.
  • A mailbox that fails does not stop the others. The failure is logged and the worker moves on.
  • The body is cleaned before it is stored. Anything active in an inbound message is removed, so a hostile email cannot become a problem in your browser.

Part sevenHow it is kept safe

This section is the short version. The long version is in docs/SECURITY.md.

Credentials never live in the database

A password is never stored in a table column, and never appears in a response, a log line or a file in the repository. What the database holds is a reference. The secret itself lives in a protected store: one file per secret, readable only by the application user, named by a hash so that listing the directory discloses nothing. The mail code fetches the value at the moment it needs it, uses it, and throws it away. It is never cached on an object.

And it is checked automatically. Every file in the repository is scanned for anything shaped like a credential, on every build. A match fails the build. The same check runs on the documentation, so a credential quoted in a document is caught too.

Signing in

  • Passwords are stored as bcrypt hashes at cost 12.
  • One session per account at a time, and expired sessions are actually cleaned up rather than piling up.
  • After too many wrong passwords the account locks for a while.
  • Every failure gives the same message, so nobody can tell from the login page whether an account exists, is disabled, or is locked.
  • Nothing about the machine is checked. There is no licence, no activation, and no hardware fingerprint.

Requests that change things

  • Every action that changes data is a proper change request, never a plain page link. A page load cannot delete anything.
  • Every such request carries a protection token, and one that arrives without it is refused.
  • Uploads are checked for size, parsed in memory, and never written to a path built from something a user typed.
  • Text that came from a user is escaped by default when it is shown again.

Staying private

  • Only addresses on a permitted list can be fetched, and private network ranges are always refused.
  • Outbound calls all have time limits and size limits.
  • Background work is bounded. A large file cannot create an unbounded number of tasks.
  • Every query for tenant data is scoped to the tenant.

Part eightRunning it

The quick way

cp .env.development.example .env.development   # set the database password
docker compose up -d --build
# open http://127.0.0.1:8083
# sign in as "admin" with the password from BOOTSTRAP_PASSWORD

That starts the application and a MySQL 8 database. The database listens on the loopback interface only, so it is not reachable from the network.

The way that suits a server

./mvnw verify            # build and run the whole test suite
./mvnw spring-boot:run    # run against a database you already have

Everything is read from the environment, so the same image runs in every place.

How it is checked

The project is built around checks that run on every change and fail the build when something is wrong. There are 13 of them, and every one has a recorded result.

199tests, none failing

The application is also built into a container and started against an empty database as part of the checks, so "it starts" is something the build proves rather than something the documentation claims.
