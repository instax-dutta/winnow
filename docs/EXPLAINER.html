How this thing worked, and what we changed

This page explains the whole system in plain language. First how the old version worked, step by step, as if you were watching someone use it. Then what was actually broken, what we fixed, what we threw away, and what we deliberately left exactly as it was.

No code. No jargon without an explanation. Everything here is checked against the decompiled original, so the old behaviour described here is the real behaviour, not a guess.

old: seo-0.0.1-SNAPSHOT new: seo-0.1.0 73 secrets found in the old build 199 tests, all passing 13 of 13 checks green

Part oneWhat the application is for

It is a cold mail and lead generation tool. In plain terms: it helps a business find people who might buy something, put those people into a list, write emails to them, send a lot of emails at once from several mailboxes, and then watch those mailboxes to see who replied.

Think of it as four separate jobs that share one database and one login:

Find people

You upload a spreadsheet of website addresses. The system visits each site, reads the raw HTML, and pulls out any email addresses it can find. Those addresses go into a list you can export.

Organise them

Those addresses, plus any you typed in yourself, become clients. You sort clients into named groups so you can send to one group and not another.

Send to them

You write an email once, as a rich text document, and get it approved. Then you pick a group, pick which mailbox to send from, and press send. The system sends one message at a time and records how each one went.

Catch the replies

Every day it connects to each of your mailboxes, reads the new mail, and stores it so you can see who answered and what they said.

One important thing to keep in mind. Several different people or companies used this system, each with their own account. Everything in the database belongs to one of them. Keeping them apart is the single most important job in the whole application, and it is exactly where the old version failed. We come back to this in Part three.

Part twoHow the old version used to work

Here is the old system as it actually behaved, following a normal day.

1. You try to log inBefore it even checks your password, the app reads the network card's hardware address of the computer and compares it to one hard-coded in a settings file. Then it decodes a "licence" token and checks its expiry date.
↓
2. You build a client listUpload an Excel file of names and addresses, or add a group of clients by hand. The old version read the name and the website from the same spreadsheet column, and it read the address from the next one.
↓
3. You write a templateA rich text email. A second person approves it. Until then it cannot be used.
↓
4. You register your mailboxesFor normal sending: an address, a mail server, a port, and the app password. For Google: an OAuth client id, a client secret, a refresh token and an access token. All four were typed into the database as plain text.
↓
5. You press sendThe system looks up the recipients, checks a limit of 50,000 emails for the month, then loops through them one at a time. For each recipient it builds a mail, sends it, and writes a row saying "sent" or "failed".
↓
6. Separately, you look for leadsUpload a spreadsheet of domains. The system fires off a background task for every row at once, visits each site, and regex-matches the page for anything that looks like an email address.
↓
7. Separately, every day at 11amIt connects to each mailbox over IMAP and tries to copy new mail into a table. It also checked, every 60 seconds, for scheduled Gmail drafts to send.

The problems with that flow, in plain words

  1. Logging in was gated on the computer, not the password

    Your account only worked on the one machine whose hardware address matched a value in the settings file. Move to a new laptop and you are locked out. The licence token was checked by decoding it and reading the expiry date, without ever checking the signature that proves who issued it. Anyone who could edit the settings file could mint their own licence.

    Then, in September 2025, the licence token expired. From that day on the old application could not log anybody in, on any machine, anywhere. The error message said "Invalid username or password", so there was no way to tell what had actually gone wrong.

  2. Your own passwords were stored in plain text, and handed back to the browser

    Forty-one mail server passwords, and the OAuth secrets for two Google accounts, sat in the database as readable text. Worse, some screens sent those passwords straight back to the browser as part of their normal response. Any logged-in user could read another user's mail password by guessing a number.

    The database also had "show SQL" switched on, which means every insert was printed to the server console. The mail passwords were being written into the log files.

  3. One tenant could read another tenant's data

    The system kept track of who was logged in by putting a number in the session. That number was passed into most of the code, but eleven places ignored it. So one account could read another account's templates, another account's mailbox inbox, and every other account's scraped email addresses. It could also delete another account's client groups, and approve another account's templates.

  4. Some delete buttons were ordinary web links

    Six actions that changed data were ordinary "get this page" requests. Browsers only send protection tokens on requests that change things, so those six actions had none. That means a web page you visited could quietly delete a client group just by loading an image from this system.

  5. The "daily" limit was really a monthly one

    The code added up everything sent from the first day of the month to the last day of the month, and refused to send past 50,000. The error message said "Daily Limit Reached". There was no daily limit at all, and nothing stopped a single day from sending 50,000 emails.

  6. The inbox reader never actually found anything

    It asked the mail server for "messages received before now and after now". The only messages that match are ones received at exactly that instant, so in practice it fetched nothing, every day, forever.

  7. The lead finder had no brakes

    One background task was created for every row of your spreadsheet, all at once, into a queue with no limit. A large file would exhaust memory. Each task was given a six-hour deadline, and the thread that kicked it all off then sat there waiting for every single one to finish. The list of already-seen addresses was kept in memory for the life of the process and never cleared, so running the same file twice the second time found absolutely nothing.

  8. A spreadsheet cell could make the server visit any address you liked

    The lead finder built a web address by pasting in the contents of a cell. There was no check on what kind of address it was. A cell could point at your own server, or at the internal metadata address that cloud machines use, and the application would fetch it and store the answer.

  9. One slow thing stopped everything else

    The background job runner had exactly one thread. The daily inbox job and the every-minute send job shared it. If the inbox job hung on a mail server that never answered, the send job simply did not run that day. The mail connections had no timeout at all, so a server that went quiet would block a thread for ever.

  10. Dates were shared, mutable objects

    Several parts of the code held a date formatter as a field on a singleton object. That is not safe to use from two threads at once, and the application used two threads. Under load it produced date strings with the wrong month, or with the day and month swapped.

  11. Some parts of the code were never used

    There was a whole class for logging someone in automatically with nobody calling it. A logout controller that was an empty file. Two beans that were declared but missing the annotation that makes them exist, so the objects they described were never created and the code silently used something else. A second, unused copy of the whole lead-finding implementation.

    One of the dead methods would have given every new user the first role in the table, which is the administrator role. It was never called, so nothing happened. It was one line away from being a problem.

Part threeThe four themes

Everything above falls into one of four themes. The rebuild fixes all four, and the fixes are enforced by the automated checks rather than by good intentions.

Theme 1

It could not keep tenants apart

The tenant was a number in the session, and eleven places forgot to use it. In the rebuild the tenant is the signed-in user, it is passed explicitly into every single service method, and every repository query filters on it again. A dedicated test file with 75 checks proves that one tenant cannot read or change another tenant's data, for every repository method and every mutating operation.

Theme 2

It leaked its own secrets

Credentials were stored in plain text in the database and returned to the browser. In the rebuild a credential is never stored in the database at all. The row holds a reference, the secret lives in a separate protected store, and the mail code fetches it at the moment it needs it and throws it away. No response body, no log line and no file in the repository contains a secret. A check scans every file in the project and fails the build if one appears.

Theme 3

It was locked to one computer

The licence and hardware-address checks are gone entirely, because the project is going to be open source. There is no machine fingerprint, no activation and no licence token. What stays is ordinary login and ordinary roles, which are about who you are, not about what you bought. A check fails the build if a licence check ever reappears.

Theme 4

It broke in ordinary, boring ways

A monthly limit called a daily limit. Pagination that always said 100 rows. An inbox reader that matched no messages. One background thread for everything. No socket timeouts. A date formatter shared between threads. These are the defects that make a system feel unreliable even when nobody is attacking it, and they are the bulk of what the rebuild changes.

Part fourWhat we changed, side by side

The same table as the engineering document, in plainer words. The full list, with the exact code references, is in docs/MIGRATION-FROM-0.0.1.md.

AreaThe old versionThe new version
Signing in Refused to work on any computer but one, and stopped working on every computer when the licence expired. An ordinary account with an ordinary password. Works wherever you sign in.
Where the tenant comes from A number read out of the session, ignored in eleven places. The signed-in user, passed explicitly into every service method and filtered again in the database query.
Mail passwords Plain text in the database, printed in the log, and sent back to the browser. Not in the database at all. A reference points at a protected store; the value is fetched for the one send and dropped.
Google tokens Client secret, refresh token and access token all in plain text, all returned by one endpoint. The refresh token lives in the protected store. The access token is never written down at all.
Delete and approve actions Six of them were plain page links, with no protection token. All of them are proper change requests, so they all carry a protection token. No page load can delete anything.
Finding leads One unbounded task per spreadsheet row, a six-hour deadline, and a seen-list that was never cleared. Eight workers, a queue of 500, a deadline per domain, a cap on domains per run, and a seen-list that belongs to the run.
Which sites may be visited Whatever a spreadsheet cell said, including your own internal network. Every address is checked first. Private and internal ranges are always refused, redirects are re-checked, and every visit has a time limit and a size limit.
The send limit 50,000 a month, described as a daily limit. Separate daily, hourly and monthly limits, per account and per sending mailbox, measured from our own records.
The email subject The template's name, typed into a mail header unfiltered. A separate field, with its own length limit and validation.
Reading replies Searched for messages received at exactly one instant, so it found nothing. Reads everything since the last check, and recognises a message it has already stored, so nothing is duplicated.
Background jobs One thread for everything, so one slow job blocked the rest. A pool of threads. A job that fails is logged and the others keep going. A job that runs twice does the work once.
Mail connection timeouts None. A quiet server blocked a thread for ever. Connect, read and write timeouts, all configurable.
Dates A formatter shared between threads, which corrupts dates under load. The modern date library throughout. Every timestamp is stored with microsecond precision.
One message, many recipients One mail object reused for every recipient, so a failed send left the next one in a strange state. A fresh mail object per recipient.
The database Hand-made, with no record of changes, no foreign keys, almost no indexes, and no unique constraints anywhere. Created and versioned by a migration tool. Real foreign keys, real indexes, unique constraints, and every table in one character set.
Where files are written A hard-coded Windows path, joined to a user-supplied date without a separator. A configured directory. No path is ever built from something a user typed.
Installing it A single large file, meant for one Windows machine, with the browser engine shipped inside it. A container image and a compose file. One command starts the application and its database.
The password list page Showed every mail server password in clear text on screen. Shows only whether a password is set, never the password.

Part fiveWhat we removed

These are gone on purpose. Each one was either a security problem, a licence gate, or code that never ran.

The licence system

  • The licence token, and the code that decoded it without checking its signature
  • The check that the computer's hardware address matches a value in the settings file
  • The printing of that hardware address to the console on every sign-in attempt
  • Both values from the settings file, so a fresh install has nothing to activate

What replaced it: nothing. The project is open source, so there is no licence to check. Sign-in and roles stay, because those are about who you are rather than what you bought.

Code that never ran

  • A class for signing users in automatically, with no caller
  • A logout controller that was an empty file
  • A logout handler that was registered but never attached, and did nothing anyway
  • Two configuration methods missing the annotation that makes them exist, so the objects they described were never created
  • A second, unused copy of the whole lead-finding implementation
  • A method that would have given every new user the administrator role
  • A service that was wired in two places and used in neither

Ways to reach data that should not have been reachable

  • Two endpoints that returned every row in the table, with no owner filter
  • An export that ignored whose data it was exporting, and produced every tenant's scraped addresses in one file
  • A download whose filename was built from the dates in the request, which is a path-building primitive even though it could not be exploited in practice
  • An endpoint that posted your uploaded spreadsheet to a placeholder web address that was never filled in
  • Two paths that were allowed through the security rules but had no code behind them at all
  • A second route to the same page, spelled with a path that did not start with a slash

Things that made the application fragile

  • A six-hour deadline on a single background task
  • An unbounded queue for the lead finder
  • A shared date formatter across threads
  • A scheduler with exactly one thread
  • Mail connections with no timeout
  • A "show every SQL statement" setting that printed passwords into the logs
  • A setting that told the application to ignore errors while setting up the database

Part sixWhat we deliberately kept

This is a rebuild, not a different product. The following are unchanged on purpose, because they worked and they are what the business is built on:

  • The four jobs. Find leads, organise clients, send email, catch replies. Same order, same idea.
  • Client groups. Named groups of contacts, so you can send to one and not another.
  • The template approval flow. A template is written, submitted, and approved before it can be used. The new version adds one thing the old one lacked: editing an approved template sends it back for approval, instead of quietly continuing to use it.
  • Both sending routes. Normal SMTP mailboxes, and Google accounts through OAuth. The Google route still works from a saved draft, with the {{Domain}} placeholder filled in per recipient.
  • The scheduled send queue. A message scheduled for a future time, sent by a background job.
  • The lead export. Download the found addresses as a spreadsheet.
  • The Amazon scraper. The sidecar that drives a browser to read Amazon search results. Its contract was repaired, and it is now reached over loopback with a timeout instead of being open to anything on the network.
  • Four roles. Administrator, manager, operator, viewer. The old system had the same idea with different names, and the old names did not line up with what the code actually checked, so the home page was forbidden to everybody. That is fixed.
  • The look and feel. The same screens, the same navigation, the same Bootstrap-flavoured admin layout, rebuilt with cleaner markup and a real design system.

What cannot be moved across automatically

Two things have to be typed in again by hand, and there is no way around it:

  • The 41 mail server passwords. They were stored as plain text, so they could in principle be copied over. But they should not be, because they were sitting in a public repository. They should be revoked and replaced, and the original should be assumed to be compromised.
  • The two Google accounts' OAuth tokens. Same reasoning, and worse: a refresh token grants permanent access to a mailbox. Revoke and re-authorise.

Everything else can be moved. The order of operations is written out step by step in docs/MIGRATION-FROM-0.0.1.md, and it is about thirteen steps.

Part eightHow we know it works

Claims are worth little without a way to check them, so the rebuild is built around checks that run on every change and fail the build when something is wrong.

It actually starts

The application is built into a container, started against an empty database, and signed into. A wrong password is tried too, and is refused. The check fails if the application does not come up or if the login page is missing anything.

The schema is right

The database is thrown away, the migrations run from nothing, and the application starts against the result. Then every table, column, foreign key and index is checked, along with the character set and the rule that no column may hold a credential.

A fresh copy builds

The project is copied to a clean directory with an empty download cache and built from scratch. If it only ever worked because of something left lying around, this is what catches it.

Nothing sensitive is committed

Every file in the project is scanned for anything shaped like a credential. The rules that came from the root instructions file, including the rule that no licence check may exist, are checked by a program rather than by a reader.
